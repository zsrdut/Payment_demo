# Payment Demo

纯模拟支付回调教学基线。用于演示“排查 → 方案 → 修复 → 独立验证 → 人工验收”的研发交付过程。

**不是生产支付系统，不移动资金，不连接真实支付通道。本分支有明确教学缺陷，验收不应全绿。**

## 环境与边界

- Python 3.10+，仅使用标准库，SQLite 随 Python 提供；不需要 pip、Docker、外部数据库或网络。
- 单商户、单渠道 `demo`、单币种 `CNY`、单服务实例；每笔订单只允许一次成功支付。
- 直接调用本地 Python `PaymentService.callback` 作为回调处理边界；**没有 HTTP 服务、监听端口或公网接口**。这版刻意剥离网络层，集中验证持久化、并发与事务语义。
- 金额单位为整数分。所有订单 ID、渠道交易号均为合成值；测试签名密钥运行时随机生成，完成后销毁，不向日志打印。
- 不包含退款、部分支付、多次支付、外部消息投递或跨节点一致性，不宣称端到端 exactly-once。

## 快速验证

在仓库根目录运行（macOS/Linux 用 `python3`；Windows 可用 `python`）：

```sh
python3 run_checks.py --expect-baseline
python3 run_checks.py
```

第一条检查教学基线是否符合预设：AC-01/04/05/07/08 通过，AC-02/03/06 失败，无执行错误。退出 0 只代表**预期缺陷成功复现**，不是修复成功。

第二条运行真实修复验收：基线应退出 1；只有八项全部通过、没有跳过或执行错误时才退出 0。**修复后的验收必须使用第二条，不带 `--expect-baseline`。**

证据输出（必须选择尚不存在的文件，避免覆盖）：

```sh
python3 run_checks.py --expect-baseline --output ./evidence/baseline-first.json
python3 run_checks.py --output ./evidence/candidate-first.json
```

输出包含实际测试记录、失败列表、环境与源码 SHA-256。测试数据使用自动创建的临时目录，不访问原有文件。仅删除本次测试创建的临时数据；已有数据库的 `initialize()` 会拒绝覆盖。

验证 Agent 如被限制只能在报告目录内写入，可将 `TMPDIR`（Windows 为 TEMP/TMP）与 `--output` 指向其获准的报告目录，并设置 `PYTHONDONTWRITEBYTECODE=1`，不能绕过执行权限。目录需存在且由平台允许；否则报告环境受阻。

## 业务规则

输入为包含以下字段的字典：`event_id`、`channel`、`transaction_id`、`order_id`、`amount_minor`、`currency`、`status`、`signature`。字段集合须完整，无额外字段。签名通过 `sign(payload, random_key)` 生成，签名覆盖除 signature 外的全部输入。

1. 验签与参数验证先于持久化变更。未知订单、金额/币种不符、不合法签名不得改变业务状态。
2. 幂等身份为 `(channel, transaction_id)`；相同交易、相同字段的合法重试（包括不同 event_id）应返回 `already_processed`，不新增成功事件。
3. 相同交易但订单、金额、币种冲突时抛出 `CallbackError`。已成功订单收到其他交易号也拒绝。
4. 首次成功返回 `accepted`。合法非成功通知返回 `ignored`，不改变成功状态或新增事件。
5. 订单更新、支付去重记录、成功事件在同一 SQLite 事务中写入；失败应回滚全部变更。
6. `inject_failure` 是测试调用参数，不能作为业务请求字段。它只作用于测试事务，不访问其他服务。

## 八项验收

- AC-01：首次合法成功，订单 paid、支付记录 1、成功事件 1。
- AC-02：4 次顺序重放（含不同事件编号），仅第一次 accepted，其余 already_processed；事件仍为 1。
- AC-03：每轮 10 个并发调用，共 3 轮、各用独立订单；同步起跑、实际调用区间重叠可查；每轮只接受一次，其余判为已处理。
- AC-04：无效签名、缺字段、未知订单、金额/币种不符、布尔金额、畸形签名均拒绝；合法重试仍能成功。
- AC-05：同一交易的业务字段冲突、同一成功订单出现另一交易，均拒绝且不覆盖已有状态。
- AC-06：新 Python 进程复用同一数据库和运行时测试密钥，重放不新增事件。模拟进程重启，不重建数据库。
- AC-07：事务内注入异常，订单/支付/事件均回滚；随后合法重试成功一次。
- AC-08：不同订单独立成功，失败通知被忽略，初始化不覆盖已有数据库。

并发规模只是教学用例，不是吞吐量、SLA 或性能压测结论。

## 已知教学缺陷

`callback` 对合法重复成功通知没有在持久化身份确认后结束处理，而继续创建成功事件。因此顺序重放、并发重放与新进程重放都会失败。基线保留此缺陷，供后续修复任务完成。正常路径、验签、冲突检查与事务回滚不是故意破坏的。

修复任务只能在**另行授权的分支**上修改，不直接改动已发布的基线。不能删测试、放宽断言、把真实验收标记为预期失败或伪造证据。遇到环境错误，应独立记录为受阻。

## 文件

- `payment_service.py`：模拟业务逻辑及 SQLite 数据模型。
- `test_acceptance.py`：八项验收用例，真实失败不隐藏。
- `run_checks.py`：验收与基线契约检测入口。
- `AGENTS.md`：执行边界和验收要求。
